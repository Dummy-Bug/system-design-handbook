### #1 — Minimum Removals to Achieve Target XOR

| Field | Value |
|-------|-------|
| Date | 2026-05-16 |

| Rating | 1745 |
| AC | Y |
| Time | 55min (clean solve — no hint, no editorial) |
| Pattern | Subset DP — memoize on (currXor, index) |
| Revision due | 2026-05-30 |

> **Note:** Context was lost before thought process was logged. Clean solve entry — solution and approach only.

---

#### Approach

At each index, two choices: keep the element (XOR it in) or remove it (count +1). Memoize on `(currXor, i)` — the current accumulated XOR and the current index. Base case: `i < 0`, check if `currXor == target`.

Impossible sentinel: `n + 1` (one more than max possible removals). Any result equal to `n + 1` is treated as impossible. Using `-1` as the sentinel would clash with the `-1` used for "not yet computed" in the DP table.

Two early exits before entering DP:
1. `highest == 0`: all elements are 0, XOR of any subset is 0. If `target == 0` return 0, else return -1.
2. `target > maxXor`: XOR of any subset cannot set a bit that no element has, so if target requires a bit above the highest element's bit-width, it's impossible.

DP table size: `(maxXor + 1) × n`. With `nums[i] ≤ 10^4 < 2^14`, `maxXor ≤ 16383`. Table is at most `16384 × 40 ≈ 655K` — fine.

O(n × maxXor) time and space.

**Why this DP works here — and when it doesn't:**
It works because `nums[i] ≤ 10^4` caps `maxXor` at 16383 → table is `16383 × 40 ≈ 655K`. Manageable.

If `nums[i]` could reach 10^9, the highest XOR bit would be bit 29 → `maxXor ≈ 2^30 ≈ 1 billion`. DP table: `1,073,741,823 × 40` entries at 4 bytes each = **~160 GB**. Completely infeasible.

MITM has no such dependency — it only cares about n, not the value range. `2^20 ≈ 1M` subsets per half regardless of how large `nums[i]` gets. MITM is the general solution; this DP is an exploit of the tight value constraint.

#### XOR technique cross-reference (from 1650-1700 band)

Same accumulated-XOR-as-state pattern used in **#6 (Longest Subarray with XOR Zero)** — track `currXor` as you move through elements; when `currXor == targetXor`, you've found a valid subset. The DP here is the same idea: instead of a prefix array, the XOR state is threaded through the recursion and memoized.

Also reuses the **bit-width bounding** from **#7 (Unique XOR Triplets I)** — `32 - Integer.numberOfLeadingZeros(highest)` gives the number of bits needed, and `(1 << bitLength) - 1` gives the XOR ceiling. Any target above that ceiling is impossible.

---

#### Alternative: Meet in the Middle

n ≤ 40 is the classic MITM signal — too large for O(2^n) brute force but small enough for O(2^(n/2)).

**Core insight:** you need `XOR(SL) ^ XOR(SR) = target` → for any left subset with XOR value `xL`, the right subset must have XOR value `target ^ xL`.

**Algorithm:**
1. Split `nums` into left half and right half
2. Enumerate all 2^20 subsets of the right half → build a map: `xorValue → maxKept`
3. Enumerate all 2^20 subsets of the left half → for each `(xL, kL)`, look up `target ^ xL` in the right map
4. If found: candidate = `kL + rightMap[target ^ xL]`. Track maximum total kept.
5. Answer = `n - maxKept`. If no valid pair found, return -1.

Right map stores `xorValue → maxKept` — for each XOR value only the best (highest) kept count matters.

O(2^(n/2)) time and space ≈ O(2^20) ≈ 1M. Value-range independent — works even if `nums[i]` reaches 10^9 where the DP table would be 160 GB.

### #2 — Pythagorean Distance Nodes in a Tree

| Field | Value |
|-------|-------|
| Date | 2026-05-16 |
| Link | https://leetcode.com/problems/pythagorean-distance-nodes-in-a-tree/description/ |
| Rating | 1725 |
| AC | Y |
| Time | — |
| Pattern | Multi-source BFS — distance arrays from fixed nodes |
| Revision due | 2026-05-30 |

---

#### Thought process

**First instinct (rejected):** Pre-order traversal — store nodes in a traversal array, use index difference as distance. Rejected immediately — index difference in pre-order is not the same as shortest path distance in the tree. Pre-order index gap can be arbitrarily wrong.

**Correct insight:** x, y, z are the only fixed nodes — every query involves distance to one of these three. So run BFS once from each of x, y, z and store distances in three arrays `dx[]`, `dy[]`, `dz[]`. For any node u, `dx[u]`, `dy[u]`, `dz[u]` are available in O(1). Then iterate all n nodes, sort the three distances, check `a² + b² == c²`.

**Why BFS, not Dijkstra:** All edges are unweighted (unit cost). BFS gives shortest distances in O(n). Dijkstra adds O(n log n) overhead with no benefit here.

---

#### Approach

Three BFS runs from x, y, z respectively → three distance arrays. Final pass over all nodes: sort `[dx[u], dy[u], dz[u]]`, check if smallest² + middle² == largest². Count matches.

O(n) per BFS × 3 + O(n) final pass = O(n) total.

---

#### Memory & constant-factor optimization (primitive arrays over maps)

First-pass solve used `Map<Integer, List<Integer>>` for the graph and `Map<Integer, Integer>` for each of `dx`, `dy`, `dz`. With `n ≤ 10⁵` it passes, but pays a heavy constant.

**Cost of the map version:**
- `HashMap<Integer, Integer>` entry: ~50 bytes (key box + value box + Entry overhead + table slot)
- Adjacency `Map<Integer, List<Integer>>`: each neighbor is a boxed `Integer` inside an `ArrayList`, plus ArrayList headers per node
- `get` / `put` / `containsKey`: ~10⁷ ops/sec ceiling vs ~10⁸ for raw array access — a 10× constant factor

At n = 10⁵ with 4 maps (graph + dx + dy + dz) and 2(n-1) directed edges, this is tens of MB heap and ~10⁷ map operations — survives, but on a tighter problem it would TLE/MLE.

**Primitive-array version (node ids are dense `[0, n)`, so `int[]` indexes directly):**
- Graph: `List<Integer>[] graph = new List[n]` populated in the edge loop. Better: CSR-style `int[]` adjacency built via degree-count + offset for fully primitive storage.
- Distances: `int[] dx = new int[n]; Arrays.fill(dx, -1);` — `-1` marks unvisited (replaces `containsKey`).
- BFS: `ArrayDeque<int[]>` is fine; tighter is two parallel `int[]` queues (node + distance) or a manual ring buffer to avoid `int[]` allocations per node.

**Reflex rule:** when node ids are already `[0, n)`, `int[]` beats `Map<Integer, *>` every time — ~5–10× faster and ~3–5× less memory. Cross-reference `reasoning-primitives/05-tle-mle-budget.md` — Trap 5 (HashMap when array works) and Trap 3 (ArrayList<Integer> when int[] works).

### #3 — Minimum Moves to Balance Circular Array

| Field | Value |
|-------|-------|
| Date | 2026-05-16 |
| Link | https://leetcode.com/problems/minimum-moves-to-balance-circular-array/description/ |
| Rating | 1740 |
| AC | Y |
| Time | — |
| Pattern | Greedy — expand radius from deficit node |
| Revision due | 2026-05-30 |

---

#### Thought process

**Feasibility check first:** If no negative element exists, answer is 0. If sum of all elements < 0, return -1 — the deficit exceeds total available balance across the array.

**Core greedy:** At most one negative element exists (guaranteed by constraints). For that deficit node at index i, expand a radius outward in both directions simultaneously (left pointer and right pointer). Drain the nearest neighbors first — borrowing 1 unit from distance d costs d moves, so closest is always cheapest. For each radius r, borrow as much as available from left and right neighbors until the deficit hits 0.

**Circular collision:** When left and right pointers meet (array is circular, so they will eventually point to the same index), that node is only borrowed from once — not double-counted.

**Why greedy by distance is optimal:** Since cost is linear with distance, taking from closer nodes first strictly minimizes total moves. There's no scenario where skipping a closer neighbor and taking from a farther one yields a better result.

---

#### Approach

1. Find negative index. If none → return 0.
2. If total sum < 0 → return -1.
3. Two pointers: `left = i - 1`, `right = i + 1` (mod n). Expand radius from 1 outward.
4. At each radius, borrow from left and right (up to their balance) until deficit = 0. Cost per unit = current radius.
5. When `left == right` (pointers meet on circular array), borrow from that node only once.

O(n) time.

**Alternative — BFS framing:** Same problem can be viewed as BFS from the deficit node — expand level by level, each level = distance r, drain neighbors in BFS order. Equivalent to the two-pointer expand. Two-pointer is cleaner here since there's exactly one deficit node, but BFS is a valid framing of the same greedy.

### #4 — Maximum Points Tasks With Two Techniques

| Field | Value |
|-------|-------|
| Date | 2026-05-17 |
| Link | https://leetcode.com/problems/maximum-points-tasks-with-two-techniques/ |
| Rating | 1703 |
| AC | Y |
| Time | — |
| Pattern | Greedy + top-k via min-heap of size k |
| Revision due | 2026-05-31 |

---

#### Thought process

**Reframe:** default answer is `Σ max(t1[i], t2[i])` — pick the better technique per task. The constraint "at least k tasks must use technique1" only matters when, for some of those k, `t2[i] > t1[i]` — those tasks lose `t2[i] - t1[i]` points when forced to t1.

To minimize total loss, pick the k tasks where forcing t1 hurts least — i.e., the k tasks with the largest `diff[i] = t1[i] - t2[i]`. Tasks where `diff ≥ 0` already prefer t1, so forcing them is free or beneficial.

**Top-k largest via min-heap of size k:** standard pattern — keep a min-heap of the k best diffs seen so far. For each new `diff[i]`, if heap not full → push; else if `diff[i] > heap.peek()` → pop and push. End state: heap holds the k tasks to force.

Final sum: for forced indices, add `t1[i]`; for the rest, add `max(t1[i], t2[i])`.

---

#### Bugs caught during review (before AC)

1. **`PriorityQueue<Integer[]>` with no comparator** — `Integer[]` is not `Comparable`. Throws `ClassCastException` on first sift. Fix: pass a comparator and use `int[]`.

2. **Two `if`s instead of `if / else if`** on the boundary iteration. When the heap first reaches size `k` after an offer, the second `if` also fires; if `diff[i]` is not the new min, it polls a smaller element and offers `diff[i]` again — `diff[i]` ends up in the heap twice, eating two of the k slots.

   Concrete trace: k=3, diffs `[1,2,3]`. After i=2, heap = `{1,2,3}`. Second `if` peeks 1 < 3 → polls 1, offers 3. Heap = `{2,3,3}`. Index 0 silently lost from the forced set.

3. **Marker via `diff[index] = -1`** — works here only because problem constraints make `-1` an impossible diff. Cleaner: separate `boolean[] forced` array. No risk of collision with a real diff value.

---

#### Approach

1. Build `diff[i] = t1[i] - t2[i]` and a min-heap of size k keyed on diff (`int[]{diff, index}`).
2. For each i: if heap size < k → offer; else if `peek().diff < diff[i]` → poll + offer. (`else if`, not two `if`s.)
3. Drain heap into `boolean[] forced` to mark the k chosen indices.
4. Sum: forced → `t1[i]`, else → `max(t1[i], t2[i])`.

O(n log k) time, O(n) space. Guard the swap branch with `k > 0` so peek isn't called on an empty heap when k = 0.

### #5 — Count the Number of Computer Unlocking Permutations

| Field | Value |
|-------|-------|
| Date | 2026-05-17 |
| Link | https://leetcode.com/problems/count-the-number-of-computer-unlocking-permutations/description/ |
| Rating | 1750 |
| AC | Y |
| Time | — |
| Pattern | Combinatorics — strict-min check + (n-1)! |
| Revision due | 2026-05-31 |

---

#### Thought process

**Reframe the unlock constraint:** for each label `i ≥ 1`, unlocking it requires some label `j < i` (in original index order) with `complexity[j] < complexity[i]` AND that `j` already unlocked. Label 0 is always unlocked first (it's the root).

**Key realisation — label 0 is a universal predecessor when it's the strict min:** if `complexity[0]` is strictly less than every other element, then for every `i ≥ 1`:
- `0 < i` ✓ (label order)
- `complexity[0] < complexity[i]` ✓ (strict min)
- Label 0 is already unlocked ✓

So label 0 alone can serve as predecessor for any other label, in any order. The remaining n-1 labels can therefore be unlocked in **any permutation** → answer is `(n-1)!` mod 1e9+7.

**Why answer is 0 otherwise:**
- If some `complexity[j] = complexity[0]` for `j > 0`: label `j` needs `k < j` with `complexity[k] < complexity[j] = complexity[0]`. But `complexity[0]` is the overall min, so nothing is strictly less. Label `j` is permanently locked.
- If some `complexity[j] < complexity[0]`: same reasoning — the global min at index > 0 has no smaller-indexed predecessor with smaller complexity.

---

#### Bug caught during review

Initial check used the global min computed over the whole array:

```java
int min = Integer.MAX_VALUE;
for (int num : complexity) min = Math.min(num, min);
if (min <= complexity[0]) return 0;
```

This is tautological — `complexity[0]` is part of the loop, so `min ≤ complexity[0]` is always true → function always returns 0.

Fix: compute the min over `complexity[1..n-1]` only, then compare:

```java
int min = Integer.MAX_VALUE;
for (int i = 1; i < n; i++) min = Math.min(min, complexity[i]);
if (min <= complexity[0]) return 0;
```

Equivalent rule: `complexity[0]` must be the **strict minimum** of the array.

---

#### Trap — sorting destroys the constraint

First instinct was "sort the array, if sorted[0] == sorted[1] return 0 else (n-1)!". This is wrong because the constraint `j < i` refers to **original labels**, not complexity-sorted positions. Sorting throws away which index holds which value.

Counter-example: `complexity = [3, 1, 2]`. Sorted is `[1, 2, 3]`, sorted[0] ≠ sorted[1] → "sort heuristic" says `2! = 2`. But real answer is 0: label 1 (complexity 1) needs `j < 1` with smaller complexity. Only label 0 exists, with complexity 3 > 1. Dead.

**Mental model fix:** the permutation is the unlock sequence over **labels**. Label 0 is always at position 0. Sorting the complexity array would move values to different labels and break the label-based constraint.

---

#### Approach

1. Find min of `complexity[1..n-1]`.
2. If `min ≤ complexity[0]` → return 0.
3. Else return `(n-1)!` mod `1e9 + 7`.

O(n) time, O(1) space.

### #6 — Distinct Points Reachable After Substring Removal

| Field | Value |
|-------|-------|
| Date | 2026-05-17 |
| Link | https://leetcode.com/problems/distinct-points-reachable-after-substring-removal/description/ |
| Rating | TBD |
| AC | Y |
| Time | — |
| Pattern | Sliding window + final coordinate decomposition |
| Revision due | 2026-05-31 |

---

#### Thought process

**Core insight (self-derived):** every move shifts x or y by ±1 independently. The final coordinate without any removal is `(px, py)` where `px = sum of all x-deltas`, `py = sum of all y-deltas`.

When you remove a substring (a window of length `k`), the characters inside the window no longer contribute. If `(wx, wy)` is the sum of deltas inside the window, the new final coordinate is `(px - wx, py - wy)`.

So the problem reduces to: slide a window of length k across `s`, compute `(wx, wy)` per window, and count the distinct `(px - wx, py - wy)` values. O(n).

**Why this works:** moves are commutative — `L` then `R` ends at the same place as `R` then `L`. The final coordinate depends only on the multiset of moves executed, not their order. Removing any window of length k just removes those k moves' contributions.

---

#### Bugs caught during review

1. **`Set<int[]>` doesn't deduplicate.** Java arrays use reference equality — `new int[]{1,2}` and `new int[]{1,2}` are different objects. Must encode the pair into a single hashable value (`Long`, `String`, or boxed wrapper with `equals`/`hashCode`).

2. **Window not fully built before first use.** Original code checked `j - i + 1 < k` and `continue`'d before incrementing the window — meaning at the iteration when window first hits size k, the current char `s[j]` was still missing from `(wx, wy)` when the subtraction happened.

   Fix: always add `s[j]` to the window first, then check if size == k, then compute and slide.

---

#### Three ways to dedupe `(int, int)` pairs in a Set — pick one

This problem (and any with 2D coordinate dedup) needs encoding the pair as a single hashable key. Three valid options, ordered simplest → most bit-trick:

**Trick 1 — String concatenation with a separator:**
```java
set.add((px - wx) + "," + (py - wy));
```
The comma is essential — without it, `(5, 5)` and `(55, "")` collide, as do `(1, 23)` and `(12, 3)`. Slowest (allocates a String per insert), but obviously correct. No magic constants, no bit fiddling.

**Trick 2 — Multiplication offset (range-aware):**
```java
set.add((long)(px - wx) * 200001 + (py - wy));
```
Treat the result space as a flat grid: 200001 columns × 200001 rows. `final_x` ranges over `[-10⁵, +10⁵]` (200001 values) because `|final_x| + |final_y| ≤ n - k ≤ 10⁵`. Same for `final_y`. The formula is `row * numCols + col` — same trick as flattening a 2D array into 1D.

The `(long)` cast prevents int overflow before multiplication.

Why 200001 is enough: every final coordinate comes from executing `n - k ≤ 10⁵` unit moves, so a single axis is bounded by `±10⁵`.

**Trick 3 — Bit packing into a long:**
```java
long key = ((long)(px - wx) << 32) | ((py - wy) & 0xFFFFFFFFL);
set.add(key);
```
Top 32 bits hold x, bottom 32 bits hold y. The `& 0xFFFFFFFFL` mask is needed because Java sign-extends a negative `int` to 64 bits when widening — without the mask, a negative y would set the upper 32 bits and collide with x. The mask zeroes those upper bits.

Works for any int range — no magic constant needed.

**Trade-offs:**

| Trick | Speed | Readability | Needs constant? |
|---|---|---|---|
| String | Slowest | Highest | No |
| Multiplication | Fast | Medium | Yes (range) |
| Bit packing | Fastest | Lowest | No |

For contests: pick whichever feels most natural to type correctly under pressure. String is the "no-think" option. Multiplication is the contest default once you've seen it once. Bit packing is the "look at me" option — clean if you internalise it, dangerous if you forget the mask.

---

#### Approach

1. Compute `(px, py)` — total deltas over `s`.
2. Slide a window of length k. Maintain `(wx, wy)` as you go.
3. When window size hits k: encode `(px - wx, py - wy)` into a long, add to set. Then subtract the leftmost char's delta from `(wx, wy)` and advance.
4. Return `set.size()`.

O(n) time, O(n - k + 1) space for the set.
