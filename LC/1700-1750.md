### #1 — Minimum Removals to Achieve Target XOR

| Revision due | 2026-05-30 |

> **Note:** Context was lost before thought process was logged. Clean solve entry — solution and approach only.

---

#### Approach

At each index, two choices: keep the element (XOR it in) or remove it (count +1). Memoize on `(currXor, i)` — the current accumulated XOR and the current index. Base case: `i < 0`, check if `currXor == target`.

Impossible sentinel: `n + 1` (one more than max possible removals). Any result equal to `n + 1` is treated as impossible. Using `-1` as the sentinel would clash with the `-1` used for "not yet computed" in the DP table.

Two early exits before entering DP:
1. `highest == 0`: all elements are 0, XOR of any subset is 0. If `target == 0` return 0, else return -1.
2. `target > maxXor`: XOR of any subset cannot set a bit that no element has, so if target requires a bit above the highest element's bit-width, it's impossible.

DP table size: `(maxXor + 1) × n`. With `nums[i] ≤ 10^4 < 2^14`, `maxXor ≤ 16383`. Table is at most `16384 × 40 ≈ 655K` — fine.

O(n × maxXor) time and space.

**Why this DP works here — and when it doesn't:**
It works because `nums[i] ≤ 10^4` caps `maxXor` at 16383 → table is `16383 × 40 ≈ 655K`. Manageable.

If `nums[i]` could reach 10^9, the highest XOR bit would be bit 29 → `maxXor ≈ 2^30 ≈ 1 billion`. DP table: `1,073,741,823 × 40` entries at 4 bytes each = **~160 GB**. Completely infeasible.

MITM has no such dependency — it only cares about n, not the value range. `2^20 ≈ 1M` subsets per half regardless of how large `nums[i]` gets. MITM is the general solution; this DP is an exploit of the tight value constraint.

#### XOR technique cross-reference (from 1650-1700 band)

Same accumulated-XOR-as-state pattern used in **#6 (Longest Subarray with XOR Zero)** — track `currXor` as you move through elements; when `currXor == targetXor`, you've found a valid subset. The DP here is the same idea: instead of a prefix array, the XOR state is threaded through the recursion and memoized.

Also reuses the **bit-width bounding** from **#7 (Unique XOR Triplets I)** — `32 - Integer.numberOfLeadingZeros(highest)` gives the number of bits needed, and `(1 << bitLength) - 1` gives the XOR ceiling. Any target above that ceiling is impossible.

---

#### Alternative: Meet in the Middle

n ≤ 40 is the classic MITM signal — too large for O(2^n) brute force but small enough for O(2^(n/2)).

**Core insight:** you need `XOR(SL) ^ XOR(SR) = target` → for any left subset with XOR value `xL`, the right subset must have XOR value `target ^ xL`.

**Algorithm:**
1. Split `nums` into left half and right half
2. Enumerate all 2^20 subsets of the right half → build a map: `xorValue → maxKept`
3. Enumerate all 2^20 subsets of the left half → for each `(xL, kL)`, look up `target ^ xL` in the right map
4. If found: candidate = `kL + rightMap[target ^ xL]`. Track maximum total kept.
5. Answer = `n - maxKept`. If no valid pair found, return -1.

Right map stores `xorValue → maxKept` — for each XOR value only the best (highest) kept count matters.

O(2^(n/2)) time and space ≈ O(2^20) ≈ 1M. Value-range independent — works even if `nums[i]` reaches 10^9 where the DP table would be 160 GB.

### #2 — Pythagorean Distance Nodes in a Tree

| Field | Value |
|-------|-------|
| Date | 2026-05-16 |
| Link | https://leetcode.com/problems/pythagorean-distance-nodes-in-a-tree/description/ |
| Rating | 1725 |
| AC | Y |
| Time | — |
| Pattern | Multi-source BFS — distance arrays from fixed nodes |
| Revision due | 2026-05-30 |

---

#### Thought process

**First instinct (rejected):** Pre-order traversal — store nodes in a traversal array, use index difference as distance. Rejected immediately — index difference in pre-order is not the same as shortest path distance in the tree. Pre-order index gap can be arbitrarily wrong.

**Correct insight:** x, y, z are the only fixed nodes — every query involves distance to one of these three. So run BFS once from each of x, y, z and store distances in three arrays `dx[]`, `dy[]`, `dz[]`. For any node u, `dx[u]`, `dy[u]`, `dz[u]` are available in O(1). Then iterate all n nodes, sort the three distances, check `a² + b² == c²`.

**Why BFS, not Dijkstra:** All edges are unweighted (unit cost). BFS gives shortest distances in O(n). Dijkstra adds O(n log n) overhead with no benefit here.

---

#### Approach

Three BFS runs from x, y, z respectively → three distance arrays. Final pass over all nodes: sort `[dx[u], dy[u], dz[u]]`, check if smallest² + middle² == largest². Count matches.

O(n) per BFS × 3 + O(n) final pass = O(n) total.

### #3 — Minimum Moves to Balance Circular Array

| Field | Value |
|-------|-------|
| Date | 2026-05-16 |
| Link | https://leetcode.com/problems/minimum-moves-to-balance-circular-array/description/ |
| Rating | 1740 |
| AC | Y |
| Time | — |
| Pattern | Greedy — expand radius from deficit node |
| Revision due | 2026-05-30 |

---

#### Thought process

**Feasibility check first:** If no negative element exists, answer is 0. If sum of all elements < 0, return -1 — the deficit exceeds total available balance across the array.

**Core greedy:** At most one negative element exists (guaranteed by constraints). For that deficit node at index i, expand a radius outward in both directions simultaneously (left pointer and right pointer). Drain the nearest neighbors first — borrowing 1 unit from distance d costs d moves, so closest is always cheapest. For each radius r, borrow as much as available from left and right neighbors until the deficit hits 0.

**Circular collision:** When left and right pointers meet (array is circular, so they will eventually point to the same index), that node is only borrowed from once — not double-counted.

**Why greedy by distance is optimal:** Since cost is linear with distance, taking from closer nodes first strictly minimizes total moves. There's no scenario where skipping a closer neighbor and taking from a farther one yields a better result.

---

#### Approach

1. Find negative index. If none → return 0.
2. If total sum < 0 → return -1.
3. Two pointers: `left = i - 1`, `right = i + 1` (mod n). Expand radius from 1 outward.
4. At each radius, borrow from left and right (up to their balance) until deficit = 0. Cost per unit = current radius.
5. When `left == right` (pointers meet on circular array), borrow from that node only once.

O(n) time.

**Alternative — BFS framing:** Same problem can be viewed as BFS from the deficit node — expand level by level, each level = distance r, drain neighbors in BFS order. Equivalent to the two-pointer expand. Two-pointer is cleaner here since there's exactly one deficit node, but BFS is a valid framing of the same greedy.
