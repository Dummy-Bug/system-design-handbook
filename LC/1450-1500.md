### #1 — Merge Close Characters
**Link:** https://leetcode.com/problems/merge-close-characters/description/
**Date attempted:** 2026-04-26
**Pattern:** build-forward / incremental-result with hash of last position
**Tag:** Partial-derive (data structure hinted, index insight derived solo)

**Insight:**
The result array IS the post-merge string by construction. Store result-index in the hash, not input-index — no bookkeeping needed.

**Invariant:**
Chars already in the result array are guaranteed to be a prefix of the final answer.

**Gap I hit:**
Tried tracking global deletion count to translate input-idx → effective-idx. Broke on "abbacdac" because deletions *after* the stored char don't shift it. Fix: store result-idx directly.

**Complexity:**
O(n) time, O(n) space. Brute force was O(n²) (single-hash scan is O(n), × n deletions = n²) — initial estimate of O(n³) was wrong.

**Tie-break ("smallest left, then smallest right"):**
Satisfied automatically by left-to-right processing. By the time we reach index i, all earlier merges are resolved, so any merge fired at i has the smallest-left-index possible at that moment. We hit r1 before r2, so smallest right index too. No extra logic needed.

**What was derived vs hinted:**
- Derived solo: cascade trap ("abba"), constraint-aware brute-force decision, parking the tie-break note, the result-index insight, the invariant articulation
- Hinted by colleagues: the build-forward data structure (array + hashmap)
- Wobbly: complexity reasoning (said n³, was n²); tie-break phrasing tangled

### #2 — Longest Balanced Substring
**Link:** https://leetcode.com/problems/longest-balanced-substring/
**Date attempted:** 2026-04-28 (first attempt, 34 min, no AC) → upsolve 2026-04-29 (2×30min, AC)
**Pattern:** O(n²) brute-force / min==max-freq
**Tag:** Upsolve (2 sessions to derive correctly)

**What "balanced" means:**
Every distinct character in the substring appears the same number of times. `"zabc"` is balanced (each appears once). `"zzabccy"` is not (z and c appear twice, others once).

**Insight:**
Track a frequency map as you extend `j`. The window `[i, j]` is balanced if and only if `min_freq == max_freq`. When balanced, length = `j - i + 1`.

**The bug I hit:**
Used `minValue * map.size()` as the answer to maximize — but this is the **condition check**, not the length. For `"zzabccy"` at full window: `{z:2, a:1, b:1, c:2, y:1}`, min=1, size=5 → outputs 5, but the window isn't balanced. Fix: only update maxLength when `min == max`, and use `j - i + 1` as the length.

**Two equivalent conditions:**
- `min == max` → window balanced → take `j - i + 1`
- `min * distinct == j - i + 1` → same thing, algebraically

**Complexity:**
O(n² × 26) = O(n²). Official editorial is also O(n²) — constraint was n=1000. Rating 1490 is for the `min==max` insight, not for optimization.

**Scope bug (caught post-AC):**
`maxValue` was declared outside the `j` loop — carries stale value across iterations. Didn't break correctness here but is logically wrong. Always declare `minValue` and `maxValue` inside the `j` loop.
