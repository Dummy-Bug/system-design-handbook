### #1 — Minimum Cost to Make Two Binary Strings Equal

**Link:** https://leetcode.com/problems/minimum-cost-to-make-two-binary-strings-equal/description/
**Date attempted:** 2026-05-20
**Rating:** 1840
**Time:** 60min — AC Y
**Pattern:** Greedy / Counting — pair mismatches by type, minimize cost per pair

**Insight:**
Only the mismatch positions matter. Classify them into two types: (1,0) where s[i]='1', t[i]='0', and (0,1) where s[i]='0', t[i]='1'. A cross-type pair — one (1,0) with one (0,1) — can be fixed with a single within-string swap at cost `swapCost`, or by flipping each individually at cost `2×flipCost`. A same-type pair — two (1,0) or two (0,1) — requires a cross-swap first to make one a different type, then a within-string swap: `crossCost + swapCost`, or again `2×flipCost` each. A lone leftover costs `flipCost`. So: pair as many cross-type pairs as possible (min(count01, count10) of them), then pair up remaining same-type, then handle any odd one out.

**Key gotcha — the hybrid case:**
The optimal may mix strategies: swap cross-type pairs but flip same-type individually (when `crossCost + swapCost > 2×flipCost`). The fix was adding a third candidate `c4`:

```
c2 = (minCount + maxCount) × flipCost           // flip every mismatch individually
c3 = cross×crossCost + swaps×swapCost + ...     // swap cross-type + cross+swap same-type
c4 = minCount×swapCost + (maxCount-minCount)×flipCost  // swap cross-type + flip same-type
answer = min(c2, c3, c4)
```

Note: a fourth case (flip cross-type + cross+swap same-type) is mathematically impossible to be optimal — if `swapCost > 2×flipCost` (favouring flip for cross-type), then `crossCost + swapCost > 2×flipCost` too (since crossCost ≥ 1), so same-type also prefers flip, which collapses back to c2.

**Complexity:**
O(n) time, O(1) space.

### #2 — Find Maximum Value in a Constrained Sequence

**Link:** https://leetcode.com/problems/find-maximum-value-in-a-constrained-sequence/
**Date attempted:** 2026-05-20
**Rating:** 1832
**Time:** ~80min — AC N (derived ~80%, missed the layered-restriction nuance; final approach understood via Socratic walkthrough, not self-derived)
**Pattern:** Slope/absolute-difference constraint between neighbors → two-pass min propagation (Candy / Trapping Rain Water family)

**Insight:**
`a[0]=0`, `|a[i]-a[i+1]| ≤ diff[i]`, restrictions cap certain indices. Maximize `max(a[i])`. Each restriction acts like a roof that pulls down its neighborhood through the slope rule. The clean formulation: compute `ub[i]` = max possible value at index `i` by propagating caps both ways:
- **Forward pass:** `l[i+1] = min(l[i+1], l[i] + diff[i])` (handles `a[0]=0` and any restriction to the left)
- **Backward pass:** `r[i] = min(r[i], r[i+1] + diff[i])` (handles every restriction to the right)
- `ub[i] = min(l[i], r[i])`, answer = `max(ub[i])`

**Key gotcha:**
My initial derivation only checked the *immediate-right* restriction, assuming the sequence "resets" at each cap. That's wrong when a later restriction is *tighter* than an earlier one — the later cap propagates back *through* the looser earlier cap. Counterexample: `n=7, restrictions=[[4,12],[2,15],[5,4],[1,6]], diff=[4,5,2,4,2,3]` — at `i=3`, immediate right is `[4,12]` giving bound 16, but `[5,4]` is tighter and forces `a[3] ≤ 10`. Fix: take min over *all* future restrictions, not just the next one. Equivalently, the two-pass min propagation handles this for free.

**Trigger to remember:**
"Absolute-value/slope constraint between neighbors" → **two passes (forward + backward), take min.** Same trick as Candy (LC 135) and Trapping Rain Water (left max / right max). Don't track only the immediate neighbor.

**Complexity:**
O(n) time, O(n) space.

**Post-mortem (Socratic walkthrough — what unlocked it):**

The intuition that finally killed the fear of this problem:

1. **`|a[i] - a[i+1]| ≤ d` means "two neighbors are within d of each other"** — symmetric. Either can be larger by up to `d`. For max, always *add* `d` when propagating in either direction. (The sign confusion was the first wall — once it's read as "within d of each other" instead of an inequality, both directions become obvious.)

2. **Each restriction `[idx, V]` propagates outward in both directions.** Walking back from `a[idx] ≤ V`: `a[idx-1] ≤ V + diff[idx-1]`, `a[idx-2] ≤ V + diff[idx-1] + diff[idx-2]`, etc. Each step adds one more diff.

3. **Every index has multiple upper bounds — take the min of all of them.** Bounds come from: `a[0]=0` (forward), each restriction (both forward and backward propagation). The trap: I assumed "only the immediate-right restriction matters" — but a further restriction with a *much smaller* V can be tighter than a closer restriction with a large V.

4. **Why one pass isn't enough — the realization that clicked:** Forward pass computes `l[i]` = max if only left-side caps existed. But forward pass can produce `l[i] = 10, l[i+1] = 4` (cap at i+1 was 4, way below `l[i] + diff[i] = 12`). Those two values *violate the slope rule between them* — they differ by 6 with `diff[i] = 2`. So `l[i] = 10` is not actually achievable; the cap at `i+1` should have pulled `a[i]` down too. The backward pass fixes exactly this — it propagates rightward caps leftward.

5. **The algorithm in one breath:** seed with `a[0]=0` + restrictions + ∞ elsewhere → forward pass `l[i+1] = min(l[i+1], l[i] + diff[i])` → backward pass in-place `l[i] = min(l[i], l[i+1] + diff[i])` → answer is `max(l[i])`.

Same trick family: Candy (LC 135), Trapping Rain Water (left max / right max). Trigger: **"absolute-value/slope constraint between neighbors" → two passes, take min.**

### #3 — Maximum Score After Binary Swaps

**Link:** https://leetcode.com/problems/maximum-score-after-binary-swaps/description/
**Date attempted:** 2026-05-20
**Rating:** 1823
**Time:** 25min end-to-end (thinking → code → AC, no hints)
**Pattern:** Regret-based greedy with max-heap — push all, pop max at each '1'

**Insight:**
Score = sum of `nums[i]` at final '1' positions. Swap allowed when `s[i]='0', s[i+1]='1'` → '1' moves LEFT, '0' moves RIGHT. So the i-th '1' from the left can end at any position `q_i ≤ p_i` (its original index), with `q_1 < q_2 < ... < q_k`. Equivalent: pick `k` positions `q_1 < ... < q_k` with `q_i ≤ p_i`, maximize sum.

The greedy: max-heap. Traverse left to right, push `nums[i]` at every index. At each '1', pop max and add to ans. At the i-th '1' (position `p_i`), the heap contains all values from `[0..p_i]` minus the `i-1` already-popped. Popping max picks the best still-available value for this 1's slot.

**Why it's correct (the part that needed thought):**
The pops don't construct a literal valid assignment — popped positions can be jumbled (e.g. pop position 2, then 1, then 0). But the *sum* is achievable by *some* valid `q_1 < q_2 < ... < q_k`. Exchange argument: if popped set is `S`, sort by position to get `r_1 < r_2 < ... < r_k`; then `r_j ≤ p_j` because at the j-th pop we'd already traversed past `p_j`. So the sum is realizable.

**Family — regret-based greedy:**
Locally-optimal choice now, but earlier candidates stay in the heap and can still be "regretted" / re-chosen later. Same pattern: IPO (LC 502), Course Schedule III (LC 630), Maximum Performance of a Team (LC 1383).

**Complexity:**
O(n log n) time, O(n) space.

### #4 — Lexicographically Smallest Array with |·| = Permutation and Sum = target

**Link:** (LC — hint-driven, rating ~1800-1850 band)
**Date attempted:** 2026-05-21
**Rating:** ~1830
**Time:** stuck → took hints from LC
**AC:** N (hinted — could not derive the greedy-from-top reframe)
**Pattern:** Greedy flip on `{1..n}` — pick largest values that fit remaining budget

**Insight:**
Start with `[1,2,...,n]`, sum `S = n(n+1)/2`. Need final sum = target. Let `D = S - target`. Flipping any `x → -x` reduces the sum by `2x`. So the task reduces to: pick a subset of `{1..n}` summing to exactly `D/2` and flip those.

Feasibility checks: `D` must be in `[0, 2S]` (target reachable) AND `D` must be even (else `D/2` not an integer, no subset works).

**Why greedy from the top works (the key insight I missed):**
Subset sums of `{1, 2, ..., n}` cover **every integer** in `[0, S]` with no gaps — because `1` is in the set and each new element `m+1 ≤ (current max reachable) + 1`. So any valid `D/2` is achievable, and greedy from `n` downward always succeeds: take `x` if `2x ≤ D` remaining; else skip.

**Why greedy from the top gives lex smallest (not just any valid answer):**
For lex smallest, position 0 dominates — make the first element as negative as possible. Flipping the **largest** values produces the **most negative** entries. Fewer-but-larger flips beat more-but-smaller flips: e.g. n=3, D=6 — flip `{3}` → `[-3,1,2]` beats flip `{1,2}` → `[-2,-1,3]` because `-3 < -2` at position 0.

**Assembly:** negatives sorted from most-negative to least-negative (i.e. `-n, -(n-1), ...` for flipped values in descending order of magnitude), then positives sorted ascending.

**Trigger to remember:**
"Permutation of `{1..n}` with sign choices, target sum, lex smallest" → think `D = S - target`, flip largest values first that fit. Greedy works because `{1..n}` has no gaps in subset sums.

**Complexity:**
O(n) time, O(n) space.

### #5 — Count Distinct Integers After Removing Zeros (digit counting)

**Link:** (LC — n ≤ 10^15)
**Date attempted:** 2026-05-21
**Rating:** ~1800
**Time:** stuck on direct counting → reframed via Socratic walkthrough
**AC:** N (the reframe came from discussion, not self-derived; walk itself was self-driven once reframe was clear)
**Pattern:** Image reframing + digit counting (digit-walk template without memoization)

**Insight — the reframe that unlocks it:**
For each `x ∈ [1, n]`, write down `strip0(x)` (remove all zero digits). Count distinct values. Naive hashset dies at `n = 10^15`. Pattern-counting duplicates (the route I tried) gets messy.

The clean reframe: **the image of `strip0` is exactly the set of no-zero positive integers ≤ n**. Proof both directions:
- Forward: `strip0(x)` always has no zeros (by definition), and `strip0(x) ≤ x ≤ n` (stripping never increases).
- Backward: any no-zero `y ≤ n` is hit by `x = y` itself, since `strip0(y) = y`.

So the question collapses to: **count no-zero positive integers in `[1, n]`**.

**Counting no-zero numbers ≤ n (the digit walk):**
Let `L = digit count of n`. Split:

1. **Part A — fewer digits:** No-zero numbers with `d` digits = `9^d` (each of `d` positions chooses from `{1..9}` independently). Sum `9^1 + 9^2 + ... + 9^(L-1)`. All are automatically `≤ n`.

2. **Part B — same digit count, ≤ n:** Walk n's digits left to right. At position `i` with n's digit `d_i`, assume the prefix `n[0..i-1]` has been matched exactly so far. Two branches at this position:
   - **Go strictly smaller here:** count of no-zero digits `< d_i` is `d_i - 1` (digits `{1, 2, ..., d_i - 1}`). The remaining `L - 1 - i` positions are free → `9^(L-1-i)` each. Contribution: `(d_i - 1) × 9^(L-1-i)`.
   - **Match `d_i` and continue:** only possible if `d_i ≠ 0` (no-zero rule). If `d_i = 0`, the walk **terminates** — no further positions contribute, and `n` itself is excluded (it contains a zero).
3. **+1 for `n` itself** if `n` contains no zeros (walk completed all positions cleanly).

**Worked example — n = 523:**
Part A: `9 + 81 = 90`.
Part B:
- Pos 0 (digit 5): `4 × 9² = 324` (smaller: {1,2,3,4})
- Pos 1 (digit 2): `1 × 9¹ = 9` (smaller: {1})
- Pos 2 (digit 3): `2 × 9⁰ = 2` (smaller: {1,2})
- n itself (no zeros): `+1`
Total: `90 + 324 + 9 + 2 + 1 = 426`.

**Edge case — n = 520 (zero in n):**
Walk reaches pos 2 with digit `0`. No no-zero digit is `< 0`, and matching `0` would violate the constraint. Walk dies. n itself also disqualified (has zero). Answer: `90 + 324 + 9 = 423`.

**Trigger to remember:**
"Count something over `[1, n]` where the property only depends on digits AND `n` is huge (10^9+)" → **digit walk**. Skeleton:
1. Closed-form sum over numbers with fewer digits.
2. Walk n's digits left to right, branching on "go smaller here" vs "match and continue".
3. Add 1 for n itself if it satisfies the property.

If "rest free" is closed-form (like `9^k` here) → no memoization needed, pure counting.
If "rest free" depends on extra state (digit sum mod k, last digit picked, etc.) → full digit DP with `(pos, tight, ...state)` memoization.

**Image-reframing as a separate trick:**
Before counting anything, ask: what does the operation's **output set** look like? If the image is a clean characterizable set, count *that* directly instead of simulating the operation.

**Complexity:**
O(L) where L = number of digits in n (≤ 16 for `n ≤ 10^15`). O(1) space.
